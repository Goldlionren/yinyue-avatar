## Relationship concurrency and restore-path safety

`relationship-update`, `relationship-overwrite`, and `relationship-restore`
all commit through `replace_relationship` while holding `avatar.lock`.
`relationship-update` now constructs its partial candidate under that same
lock, so it cannot merge against a stale pre-lock relationship.

The generation worker reads, builds, generates, and commits while holding the
same lock. A threaded test paused a worker after its old-state read, started an
author overwrite, proved the overwrite could not complete while the worker
owned the lock, released the worker, and verified the serialized author write
won last. The worker cannot later overwrite the new relationship.

Restore resolution now:

- accepts only a direct regular file in `STATE_DIR/relationship-backups`;
- rejects `..` traversal, nested names, absolute out-of-root paths, directories,
  missing files, a symlink root, and symlink backup files;
- resolves the path strictly and verifies its parent is the canonical backup
  root;
- never automatically removes relationship backups.

No prune command was added in this phase.

## Structured long-term memory

Runtime layout:

```text
STATE_DIR/memory/events.jsonl
STATE_DIR/memory/summary.json
STATE_DIR/memory/backups/
```

Implemented commands:

```text
memory-list
memory-show
memory-add
memory-supersede
memory-resolve
memory-rebuild-summary
```

Memory writes accept fixed scalar CLI arguments, not arbitrary event or summary
JSON. The helper validates type, importance 1–5, non-empty bounded text,
status, ids, and canonical SHA-256 dedupe key. Allowed types are relationship
event, shared experience, user preference, commitment, important fact, and open
thread.

Exact active duplicates return the existing id without rewriting events,
summary, or history. Supersede marks the old record and adds a linked
replacement. Resolve retains the record with resolved status. No operation
deletes events or backups.

Candidate events and summary are built and validated before replacement.
Events and summary use mode-0600 temporary files plus atomic replacement.
Before each summary update, the old summary is atomically copied to
`memory/backups`. If summary replacement fails, candidate events are rolled
back and the old summary remains unchanged. A corresponding compact history
event is appended only after the memory transaction succeeds.

`--remember` remains compatible and maps to `shared_experience`, importance 3,
with canonical dedupe. Legacy state memory is imported once when structured
events do not yet exist. Memory commands do not modify state relationship,
scene, continuity, or last image and do not create jobs or delivery calls.

## Deterministic summary

`summary.json` schema version 1 contains source count and six category arrays:
relationship events, shared experiences, user preferences, commitments,
important facts, and open threads.

The helper:

1. selects active events only;
2. deduplicates by canonical key;
3. sorts importance descending, timestamp descending, then id deterministically;
4. applies a per-category maximum;
5. applies a global text-character budget;
6. validates the complete candidate;
7. backs up the old summary;
8. atomically replaces only after successful construction.

No LLM or network service participates. Identical inputs produce identical
selection and ordering; only the explicit generation timestamp differs.
Backups are never automatically pruned.

`context` reads `summary.json`; a test placed corrupt content in
`events.jsonl` and proved context still succeeded without opening the event
store.

## Meaningful recent history

Mechanical last-five-line loading was removed from `context`. The selector
reverse-scans a bounded number of history lines and defaults to:

```text
max_events = 8
max_chars = 4000
scan_max_lines = 500
```

It accepts the required scene, relationship, author overwrite/restore, memory,
commitment, render, delivery-pending, and migration business events. Status,
doctor, polling, launcher, duplicate request, no-change update, debug, and
unknown events are ignored.

Selection keeps the newest duplicate by event id and compact business
fingerprint. Relationship, commitment, and pending delivery receive priority.
The chosen set is then returned chronologically. Count and character budgets
set `truncated`; damaged JSONL lines are counted and skipped. Full
relationship before/after objects are never copied into context: overwrite and
restore become a compact revision-change summary.

- defaults to dry-run and writes only with `--apply`;
- canonicalizes source and destination;
- requires the exact `$HOME/.hermes/skills/roleplay/yinyue-avatar` destination;
- rejects empty, relative, root, HOME, non-allowlisted, symlink, and
  source-equals-destination targets;
- creates a full tar backup and pre-deployment manifest;
- copies into a same-parent staging directory;
- preserves existing `config.local.json`;
- runs shell, JSON, all unit/mock tests, and effective workflow-baseline
  validation in staging;
- switches directories with an error trap that restores the prior Skill;
- writes staging and post-deployment manifests;
- performs only shell/JSON/hash validation after switching;
- never reads or migrates state, starts workers, submits ComfyUI, or sends
  Telegram.

The apply path was tested only with a dedicated temporary HOME. Tests proved
dry-run, dangerous-path rejection, local-config preservation, and rollback
after an injected post-switch failure. The production installer was not run.

## Isolated staging scripts

`prepare-staging.sh` and `cleanup-staging.sh` default to dry-run.

Preparation accepts only a dedicated
`/mnt/data_nvme/tmp/yinyue-avatar-staging-*` root, rejects symlink roots and
active production jobs/lock holders, copies the state into independent
state/jobs/pending/logs/output, copies the authoritative production workflow,

`telegram.enabled=false` and a blocker executable. Background launcher mode is
`disabled`. The script never invokes avatarctl or ComfyUI and only prints an
explicit foreground `--no-send` command for a later separately authorized
test.

Cleanup requires a valid non-symlink marker whose embedded root exactly matches
the canonical target. It accepts only the staging namespace and refuses a tree
containing symlinks. Apply removes exactly that validated root.

under `/mnt/data_nvme/tmp`. Path isolation, independent state path, Telegram
disablement, dry-run cleanup, symlink refusal, and marker-guarded cleanup all
passed. No generation or delivery occurred.
