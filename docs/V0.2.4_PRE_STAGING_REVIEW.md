## Long-term memory maintenance assessment

Status: **partially implemented**.

- Only caller-supplied `--remember` text enters long-term memory.
  `append_memory` strips empty input, appends it to a 20-item
  `memory.recent_events` list, and appends a bullet to
  `memory.long_term_summary` at `lib/avatarctl.py:234-245`.
- `update`, `show`, and `render` expose `--remember` at
  `lib/avatarctl.py:1056-1068`. Update applies it at
  `lib/avatarctl.py:918-937`; successful generation applies it to the candidate
  at `lib/avatarctl.py:618-669`.
- Transition, reset, generation, migration, and delivery events enter raw
  `history.jsonl` through their event paths but do not automatically enter
  long-term memory.
- The summary is not generated by an LLM and is not a true summary. It is a
  fixed string-membership check followed by unbounded bullet concatenation.
- It updates during an explicit update commit or successful generation commit.
  Generation failure leaves the candidate and summary uncommitted.
- There is no independent summarization operation, so there is no summary
  failure recovery policy.
- State replacement is atomic, but state plus history append is not one atomic
  filesystem transaction (`lib/avatarctl.py:668-669,936-937`).
- There is no old-summary backup or summary revision history.
- `append_memory` does not touch relationship, and scene helpers compare/copy
  relationship and memory independently.
- Ordinary chat does not automatically write memory, but there is no content
  classifier, event allowlist, provenance requirement, or confirmation gate.
  An Agent can pollute memory by passing arbitrary chat through `--remember`.
- No dedicated test exercises `append_memory`, summary deduplication, size
  limits, summary rollback, or chat-pollution prevention.

Therefore long-term memory is present in the state and context runtime chain,
but production-grade summary maintenance is **not implemented**.

- Allowed event types: every event type, without an allowlist.
- Ignored event types: none, except blank lines.
- Limit: five events; no token or byte budget on decoded event content.
- Ordering: original file order among the selected tail lines.
- Duplicate handling: none.
- Meaningfulness scoring/filtering: none.
- Corresponding semantic filtering tests: none.

This remains a v0.2.4 incomplete item and a production deployment blocker.

## Safe for isolated ComfyUI staging

**Conditionally yes**, but not through `scripts/install.sh`. A staging test may
use a detached checkout/copy, an explicit temporary state directory, a
non-production output directory, a staging-only config, `--no-send`, and a
separately authorized ComfyUI endpoint. It must first snapshot the staging
state and verify the v0.2.3 workflow hash. This review did not submit a real
generation.

## Unsafe for production deployment

**Yes: unsafe for production deployment.** The identified memory, recent
history, installer, relationship-management, recovery hardening, and online
staging gaps must be resolved and re-reviewed. Do not install v0.2.4 into the
production Skill and do not migrate production state.

## Post-review relationship-management correction

The later author-directed correction adds distinct `relationship-update`,
`relationship-overwrite`, `relationship-backups`, and `relationship-restore`
commands. Complete overwrite is assignment, not merge; it creates a private
atomic backup and audit event. Explicit `AUTHOR-BREAK-GLASS` can bypass the
relationship schema but not JSON-object parsing, relationship-only scope,
backup, atomic state write, or auditing. This resolves the earlier absence of a
dedicated author maintenance surface. It does not resolve the installer,
meaningful-history, long-term-summary, recovery-hardening, or online-staging
blockers, so the production deployment conclusion remains unchanged.
